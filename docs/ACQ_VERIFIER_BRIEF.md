# ゼロイチ節の検証役ブリーフ

あなたは調査役とは独立した **検証役** です。各エントリの `acquisition:` 節（最初のユーザーをどこから・どう集めたか）を原資料に当たって検査し、誤りを直し、反証を足します。調査役の結論に同調する必要はありません。

## 必読
- `docs/ACQUISITION_BRIEF.md`（形式・チャネル定義）、`docs/RESEARCH_GUIDE.md` の「絶対ルール」
- 担当エントリ `data/games/<id>.yaml` の `acquisition:` と、そこから参照される sources・metrics

## やること（エントリごと）
1. **新しく追加された出典の実在と内容**: acquisition から参照される出典を開き直す（WebFetch。github.com も可。medium/dune/dappradar/mirror は遮断されるので「この環境で再確認不可」と記録）。開けない・内容が違うものは `access` と `note` を実態に合わせる。
2. **照合**（優先順）: metrics の数値・期間・定義 → steps の日付と phase → チャネルの分類（定義表に合っているか。例: 紹介報酬を viral-mechanic にしていないか、Discord があるだけで community-server を獲得チャネル扱いしていないか）→ 「最初の」「初めて」「〜で集まった」等の強い表現 → `q` 引用の逐語性 → 他の fact。出典に書かれていなければ修正・削除・`k: analysis` への格下げ・`k: unknown` 化。
3. **因果**: 「施策 X でユーザーが増えた」が fact になっていたら analysis に。運営の説明は claim（who 付き）。
4. **反証**: 獲得の説明を否定し得る事実や別の説明（相場全体の上昇、報道、ボット・多重アカウント、賞金目当ての一時流入、数字の定義の違い）を自分で 1 件以上探し、`counter` に出典付きで追加。見つからなければ記録に書く。
5. **数値の混同**: 登録者・ウォレット・DAU・プレイヤー・取引数・売上・調達額が混ざっていないか。
6. `node scripts/validate.mjs --only <id>` で ERROR がないこと。他ファイルの YAML パースエラーが出たら少し待って再実行。

## 記録
`docs/verification/<id>.md` の末尾に次の節を **追記** する（既存の内容は消さない）:

```
## ゼロイチ節の検証（YYYY-MM-DD）
- 確認した出典: n / m
- 直したこと: before → after を一行ずつ
- 追加した反証
- 確認できなかったこと
- 判定: 重大な問題なし / 修正済み / 要再調査（理由）
```

担当外のファイルは触らない。最終報告は 150 語以内で、修正件数と重大な問題だけ。
